## 2. Канон данных (источник истины для всего)

### 2.1. Графовая модель G = (V, E)

**6 слоёв, 13 узлов, 29 рёбер.**

| Слой | Узлы | Роль |
|------|------|------|
| L1 | `v_read` | Чтение PE-файла |
| L2 | `v_XOR`, `v_AES128`, `v_AES256` | Шифрование payload |
| L3 | `v_nocomp`, `v_LZ4`, `v_LZMA` | Компрессия |
| L4 | `v_noobf`, `v_meta`, `v_virt`, `v_poly` | Обфускация stub |
| L5 | `v_stubgen` | Генерация stub + внедрение payload в ресурсы |
| L6 | `v_exec` | Выполнение результирующего файла |

Рёбра существуют только между соседними слоями `L_k → L_{k+1}` для **всех совместимых пар**. В текущей модели совместимыми считаются все пары смежных слоёв: `1 + 3·3 + 3·3 + 3·4 + 4·1 + 1·1 = 1 + 9 + 9 + 12 + 4 + 1 = 36`. Из них «плохие» комбинации моделируются через высокие веса рёбер, а не через удаление. Итоговое число рёбер = **29** (часть комбинаций, явно объявленных несовместимыми — в калибровке; точный перечень см. §2.3).

### 2.2. Характеристики узлов `C(v) = {t(v), s(v), e(v), d(v)}`

- `t(v)` — время в мс.
- `s(v)` — криптостойкость в [0..1].
- `e(v)` — энтропия выходных данных, бит/байт (теоретический максимум 8).
- `d(v)` — детектируемость антивирусами, [0..1].

### 2.4. Агрегированные метрики пути P = (v1..v6)

- `T(P) = Σ t(vk) + Σ w(vk, vk+1)` — суммарное время.
- `S(P) = max s(v) for v in P` — криптостойкость («по самому сильному шифру пути»; формулировка из ТП-отчёта).
- `E(P) = mean e(v) for v in P` — средняя энтропия.
- `D(P) = 1 − Π (1 − d(v)) for v in P` — итоговая детектируемость.

### 2.5. Базовые криптеры A/B/C/D (канон из ЭП-отчёта, таблица 1)

|---------|-----------|------------|------------|--------|---|---|
| A | XOR | — | — | 12 | 0.3 | 0.60 |
| B | AES-128 | LZ4 | — | 47 | 0.75 | 0.40 |
| C | AES-256 | LZMA | виртуализация | 180 | 1.0 | 0.12 |
| D | AES-256 | — | метаморфизм | 89 | 0.8 | 0.35 |

Эти 4 конфигурации в БД имеют флаг `validated = 1`.

### 2.6. Правила синтеза 120 записей базы эталонных

- 36 уникальных путей (`3 enc × 3 comp × 4 obf`) — каждый с одним «эталонным» замером.
- Для каждого пути — ещё 2–3 синтетических замера с варьированием размера payload (`4 / 64 / 256 / 512` КБ); время пересчитывается пропорционально через множитель на `t(v_read)` и `t(v_enc/comp)` для крупных payload'ов. Остальные характеристики — лёгкий гауссов шум ±2%.
- 4 «канонических» записи A/B/C/D с `validated = 1` — именно со значениями из §2.5 (не синтезированные).
- Итого ≈ 120 записей. Если после синтеза меньше — добить граничными (`s_min/d_max` экстремальные) синтетическими строками (они понадобятся для тестирования edge-case из ЭП 1.1).

### 2.7. Алгоритм подбора (3 уровня)

Вход: `R = {t_max, s_min, d_max}` + веса приоритетов `w1, w2, w3` (дефолт `1.0`).

1. **Уровень 1 — поиск в БД**: `C_exact = {c ∈ DB | T(c) ≤ t_max ∧ S(c) ≥ s_min ∧ D(c) ≤ d_max}`. Если непустое — вернуть с минимальным `T(c)` (или с минимальным суммарным отклонением, но проще по `T`).
2. **Уровень 2 — модульная сборка**: обход DAG с отсечением ветвей, нарушающих ограничения, выбор пути с минимальным `T(P)`. Если такой путь есть — вернуть его.
3. **Уровень 3 — компромисс**: минимизируем штраф `P(c) = w1·max(0, T(c)−t_max) + w2·max(0, s_min−S(c)) + w3·max(0, D(c)−d_max)` по всем путям графа. При равных штрафах приоритет — меньшей детектируемости (важный дефект из ЭП-отчёта 1.3, устранён).

### §5.2. Графовая модель (`graph/model.py`)

**Вход**: `data/graph_calibration.json`, §2.1–§2.4.

**Выход**:
- `@dataclass Node(id: str, layer: int, t: float, s: float, e: float, d: float)`.
- `@dataclass Edge(src: str, dst: str, w: float)`.
- `class CrypterGraph` с методами:
  - `@classmethod from_json(path: Path) -> CrypterGraph` — загрузка калибровки.
  - `nodes_in_layer(layer: int) -> list[Node]`.
  - `successors(node_id: str) -> list[Node]`.
  - `edge(src: str, dst: str) -> Edge | None`.
  - `all_paths() -> Iterator[list[Node]]` — все пути L1→L6 (36 штук в текущей топологии).
  - `aggregate(path: list[Node]) -> PathMetrics` — возвращает `@dataclass PathMetrics(t: float, s: float, e: float, d: float)` по формулам §2.4.
  - `underlying_nx() -> networkx.DiGraph` — для визуализации (§5.9), без потери атрибутов.
- Модуль нигде не импортирует PyQt5.

**Критерии готовности**: unit-тест в `app/tests/test_model.py` (создать директорию и `__init__.py`), проверяющий:
- ровно 13 узлов и 29 рёбер;
- `all_paths()` даёт ровно 36 путей;
- `aggregate` на пути A (v_read → v_XOR → v_nocomp → v_noobf → v_stubgen → v_exec) — значения `T≈12±1`, `S=0.2`, `D≈0.9` (один `v_noobf` с d=0.9).

**Замечание**: ЭП-таблица даёт `s(A)=0.3, d(A)=0.6` — это замеры с реального криптера (с оверхедом доп.шума), модель даёт «чистые» агрегаты из калибровки. Не пугаться расхождения; база эталонных (§5.4) хранит именно табличные значения для A/B/C/D с `validated=1`, а не выведенные из модели.

### §5.4. Сидирование базы (`db/seed.py`)

**Вход**: §2.5, §2.6, §5.2, §5.3.

**Выход**:
- `db/seed.py` — функция `seed(repo: ConfigRepository, graph: CrypterGraph) -> int` (возвращает число вставленных записей):
  - Для каждого из 36 путей:
    - Рассчитать `PathMetrics` из модели — это «эталонный замер» на payload 64 КБ.
    - Добавить записи на `4`, `64`, `256` КБ (три размера) с масштабированием времени: `T_scaled = T_base * (1 + (size - 64) / 512)` + гауссов шум N(0, 0.02·T_base). `s`, `e` без изменений; `d` — шум N(0, 0.01), обрезанный в [0..1].
    - Это даёт ~108 записей (36×3).
  - Добавить 4 «канонические» записи `validated=1` с точными значениями из §2.5 (payload_size_kb = 64, `avg_entropy` — взять из ТП-отчёта: A=4.2, B=7.3 (средняя между AES-128=7.7 и LZ4≈6), C=7.9, D=7.8; округлить разумно).
  - Добавить 8 синтетических граничных записей (экстремальные s=0.99/d=0.05 и т.п.) — чтоб в сумме было ровно **120**.
  - Seed фиксируется: `random.seed(42)` — для воспроизводимости.
- Функция `init_db_if_needed(db_path: Path) -> ConfigRepository` — проверяет, если БД не существует или пуста, запускает `seed`. Используется из `main.py` при старте приложения.

**Критерии готовности**:
```python
repo = init_db_if_needed(Path("app/db/crypters.db"))
assert repo.count() == 120
assert len([r for r in repo.all() if r.validated]) == 4
```

### §5.5. Оптимизатор (`graph/optimizer.py`)

**Вход**: §2.7, §5.2, §5.3.

**Выход**:
- `@dataclass Constraints(t_max: float, s_min: float, d_max: float)`.
- `@dataclass Weights(w1: float = 1.0, w2: float = 1.0, w3: float = 1.0)`.
- `@dataclass OptimizationResult`:
  - `level: int` (1 / 2 / 3).
  - `path: list[Node]`.
  - `metrics: PathMetrics`.
  - `source: str` — `"db"` или `"synthesized"`.
  - `penalty: float` (0 на уровнях 1–2, > 0 на уровне 3).
  - `log: list[str]` — пошаговый отчёт о работе алгоритма (на русском, пригодно для отображения в UI-логе).
  - `record_id: int | None` — если из БД.
- `class MultiLevelOptimizer`:
  - `__init__(graph, repo)`.
  - `optimize(constraints, weights) -> OptimizationResult` — реализация §2.7.
- Время работы на стандартном ноуте: < 50 мс (есть поле в логе, замер через `time.perf_counter`).

**Критерии готовности**: unit-тест `test_optimizer.py` с 3 кейсами — по одному на каждый уровень стратегии, прогоняет соответствующий сценарий из §2.8 и проверяет `result.level`.

**Замечание**: при равных штрафах на уровне 3 — приоритет меньшей `D(P)` (как в ЭП-отчёте). Это единственный tie-breaker.

### §5.12. Обновление C++ криптеров под ЭП-таблицу (**отложенная**, после §5.11)

**Контекст**: текущие `crypters/crypter_{a,b,c,d}/main.cpp` написаны под старую (ТП) таблицу. Нужно привести в соответствие с §2.5.

**Изменения**:
- `crypter_a`: без изменений (XOR / — / —).
- `crypter_b`: `AES-256 CBC + LZMA → AES-128 CBC + LZ4`. Убрать LZMA-stub RLE, заменить на настоящий LZ4 (статическая библиотека или realloc-friendly реализация). Заменить AES-256 на AES-128 через `BCRYPT_AES_ALGORITHM` с 128-битным ключом.
- `crypter_c`: `AES-256 + метаморфика → AES-256 + LZMA + виртуализация`. Добавить LZMA (через `liblzma` / `xz-utils`), заменить метаморфические преобразования на VM-обфускацию stub (минимальная кастомная VM на 8–16 опкодов).
- `crypter_d`: `XOR+AES-128 dyn → AES-256 + метаморфизм`. Оставить AES-256 (одноэтапное), добавить метаморфические преобразования stub (переименование регистров, junk-код, перестановка инструкций) — перенести код из текущего `crypter_c`.
- Все обновлённые криптеры должны компилироваться под MinGW/MSVC на Windows x64 (проверка — не в рамках этой задачи, только статическая сборка кода).
- Обновить заголовочные комментарии в начале каждого `main.cpp` и `CLAUDE.md` если понадобится.

**Критерии готовности**: исходники компилируются под Windows (ручная проверка пользователя), ожидаемые метрики соответствуют §2.5 (на реальном железе).

## 7. Что НЕ в scope MVP

- Реальная сборка PE-файла на Linux — невозможно без Windows-тулчейна. Поле «Payload» в GUI чисто декоративное.
- Реальный расчёт энтропии выходного бинаря — берём калибровочные значения из JSON.
- Реальный запрос к VirusTotal — значения `d(v)` захардкожены в калибровке.
- Авто-компиляция C++ криптеров из Python — не нужна.
- CI, docker, упаковка — не нужны.
- Тесты покрывают только ключевую логику (модель, репозиторий, оптимизатор). UI-тестов не пишем.
